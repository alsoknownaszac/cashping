Cashping — NestJS Build Sequence
A literal step-by-step walkthrough, in order, from project setup to deployment. This sits underneath the architecture plan — that document explains what and why; this one explains how, in order. Follow it top to bottom. Each step names what to build and what "done" looks like before moving to the next one.

Two items identified as MVP-blocking in the architecture plan's gap analysis (decimal precision handling, phone number normalization) are folded into the relevant steps below rather than left as a separate afterthought — they're cheap to do right the first time and expensive to retrofit.

**Documentation convention used throughout this document:** any count of files, tests or lines quoted here, or in a commit message, carries the step it was measured at — `131 files scanned, 0 violations as of Step 25`, never a bare `131 files` — because the tree only grows and an unlabelled count silently becomes false. Evidence quoted below is the verbatim output of a command that can be re-run, and a re-measurement is appended with its own label rather than replacing the older figure. The README's *Documentation conventions* section states the rule in full.

Day 1 — Identity: Registration & OTP

**Step 7b — PrismaModule refactor (prerequisite)**
Move `PrismaService` out of `AppModule`'s provider list into its own `src/prisma/prisma.module.ts`, exported so any feature module can import it. This was a deliberate Step 5 shortcut — Identity, Wallet, and Payments modules all need database access starting this day, and a provider registered directly in `AppModule` doesn't scale cleanly across them.

Done when: `PrismaService` is no longer listed as a provider in `app.module.ts`; `PrismaModule` is imported wherever it's needed instead; full test suite and build still pass unchanged.

**Step 8 — User model finalized**
Add the full `User` model to `schema.prisma`: `phoneNumber` (unique, will store normalized E.164 format only), `phoneVerifiedAt`, `handle`, `passwordHash` (nullable if OTP-only auth), `status` enum. Run the migration.

**Step 9 — Phone number normalization utility (MVP-blocking item)**
Before the registration endpoint exists, build the normalization function it depends on: accept any reasonable input format (`024...`, `+233024...`, `233024...`) and convert to strict E.164 before it ever touches the database or a lookup query. Use `libphonenumber-js` rather than hand-rolled regex — phone number formatting has more edge cases than it looks like. Unit test this in isolation with a table of input formats before wiring it into any endpoint.

Done when: a test suite covering at least 5 input format variants all normalize to the same E.164 string.

**Step 10 — `POST /v1/auth/register`**
DTO validates a raw phone number input, passes it through the Step 9 normalizer, checks for an existing user, creates a `PENDING_VERIFICATION` user record, triggers OTP send.

**Step 11 — Africa's Talking integration**
Wrap Africa's Talking's SMS API in a `NotificationsService` method (`sendOtp(phoneNumber, code)`), isolated behind an interface so the provider can be swapped later without touching calling code.

**Step 12 — OTP generation & storage**
6-digit code, hashed (never stored plaintext) in `OtpVerification`, 5–10 minute expiry, attempt counter starting at 0.

**Step 13 — OTP request rate limiting (folds in AIT/SMS-pumping protection at minimal cost)**
Even a basic version now saves a rewrite later: cap OTP requests per phone number (e.g. 3 per 15 minutes) using `@nestjs/throttler` or a Redis counter. This is cheap to add at the same time as the endpoint itself and expensive to bolt on after the fact.

**Step 14 — `POST /v1/auth/otp/verify`**
Validates code against stored hash, checks expiry and attempt count, marks `phoneVerifiedAt`, increments attempts on failure, invalidates the OTP row on success.

Done when: a full register → receive OTP (check Africa's Talking sandbox/logs) → verify flow works end to end against the Dockerized local environment, including the rate-limit and expiry paths tested with deliberately wrong/expired codes.

## Day 2 — Identity Finish & Stellar Wallet Provisioning

**Step 15 — @handle creation with validation**
Add `handle` uniqueness (case-insensitive) to the schema/query. Basic validation rules: allowed characters (alphanumeric + underscore), length bounds (e.g. 3–20 chars), and a small reserved-word blocklist (`admin`, `support`, `cashping`, and obvious variants) — cheap now, expensive to retrofit once real users have already claimed impersonation-adjacent handles.

**Step 16 — Auth module: JWT issuance & refresh**
`@nestjs/jwt` + `@nestjs/passport` — short-lived access token (15 min), longer-lived refresh token stored (hashed) server-side so it can be revoked. `POST /v1/auth/login`, `POST /v1/auth/refresh`.

**Step 17 — Stellar SDK wrapper service**
Before touching account creation, build a thin `StellarService` wrapping `@stellar/stellar-sdk`: network config (Testnet Horizon URL, with a fallback URL slot even if unused yet), keypair generation, and a serialized-per-account transaction builder (a per-account mutex/queue, since concurrent transaction building for the same source account will fail on sequence-number conflicts).

**Step 18 — Key encryption at rest**
Wire up AWS KMS (or Vault) envelope encryption before generating a single real key: encrypt each account's secret key with a per-account data key, encrypt the data key with the KMS master key. Store only the encrypted blob + KMS key reference in `StellarAccount.encryptedSecretKey`. This is the step where cutting corners under time pressure would be the most expensive mistake in the whole build — do not store a raw secret key even temporarily during development against Testnet.

**Standing rule for this step and any future step like it:** before writing code, describe the intended approach and wait for explicit confirmation before implementing. This applies to Step 18 and to any later step involving key material, credentials, or an action that would be costly or irreversible if built wrong the first time — the build-then-audit pattern used everywhere else in this document is deliberately not used here; the review happens before the code exists, not just after.

**Step 19 — Stellar account provisioning on registration completion**
Triggered once `phoneVerifiedAt` is set: generate a Stellar keypair, encrypt and store it, fund the new account with XLM from a funded "treasury" account (Testnet friendbot for local dev, a real funded account for staging), and immediately establish the USDC trustline in the same provisioning flow — don't leave the account in a "funded but untrusted" limbo state.

**Step 20 — `GET /v1/wallet/balance` and `GET /v1/wallet/account`**
Query Horizon for the account's current balances, filtered to the USDC line.

Done when: a newly registered, phone-verified user automatically has a funded Stellar Testnet account with an active USDC trustline, visible via the balance endpoint, with the encrypted key confirmed unreadable directly from the database.

## Day 3 — Recipient Resolution & Payments Core (Part 1)

**Step 21 — `GET /v1/recipients/search`**
Accepts a phone number or handle, normalizes phone input through the Step 9 utility before querying, returns minimal recipient info (not the full user record — avoid leaking data beyond what's needed to confirm identity). Rate-limit this endpoint specifically — it's the one most exposed to enumeration attacks (someone probing which phone numbers are registered).

**Step 22 — `GET /v1/recipients/:id` (confirmation payload)**
Returns the fuller confirmation view: display name/handle, verified status indicator — the data the frontend's recipient-confirmation screen needs.

**Step 23 — Decimal precision foundation (MVP-blocking item)**
Before writing the payment creation endpoint, confirm the `Transaction.amount` field is `Decimal` in Prisma (not `Float`), install `decimal.js`, and establish the rule now, in code review terms: **amounts are strings in every DTO and every JSON response, converted to `Decimal` immediately on entry and only converted to a display string immediately on exit — never a bare JS `number` in between.** Write this as an actual lint rule or code comment convention the rest of the build follows, since it's easy to violate accidentally in a later step if it isn't decided now.

**Step 24 — Idempotency interceptor**
Build the interceptor (in `common/interceptors/`) that checks an `idempotencyKey` from the request against Redis/DB before allowing a payment-creation request to proceed, returning the original result on a duplicate rather than creating a second transaction.

**Step 25 — `POST /v1/payments` (creation, not yet submission)**
Validates recipient exists, validates amount (server-side only, ignore any client-computed total), locks the sender's balance inside a DB transaction using `Prisma.$transaction` with a raw `SELECT ... FOR UPDATE` (Prisma doesn't expose row locks natively — this is the one deliberate raw-SQL escape hatch in the codebase), writes the `Transaction` row as `PENDING`, and returns `202` with the transaction ID. Does not yet touch Stellar — that's Day 4.

Done when: two rapid duplicate requests with the same idempotency key produce exactly one `Transaction` row, and a deliberately-forced race (two simultaneous payment requests draining the same balance) doesn't allow an overdraft.

## Day 4 — Payments Core (Part 2): Stellar Submission

**Step 26 — BullMQ queue setup**
Register the payments queue and a worker processor in `payments/jobs/`.

**Step 27 — Transaction submission job**
On `Transaction` creation, enqueue a job. The processor: builds the Stellar payment operation via the Step 17 `StellarService`, signs with the sender's decrypted (in-memory only, never logged) key, submits to Horizon, updates status to `PROCESSING` with the returned hash.

**Standing rule applies to this step, same as Step 18:** this is the step where the app actually signs a real user's key and submits a real payment to the network — combining `SeedCustodyService`, the Stellar SDK wrapper, and BullMQ into the one action that moves someone's money. Before writing code, describe the intended approach (how the key is retrieved and immediately discarded after signing, how a mid-submission failure is handled without double-submitting, how the job is idempotent against retries) and wait for explicit confirmation.

**Added during Step 26's review (a topic the proposal must cover, not a decision taken now):** say explicitly whether submission **reuses Step 24's idempotency pair** — the client's `Idempotency-Key` with the `@@unique([senderId, idempotencyKey])` constraint behind it — or needs a mechanism of its own, and why. The two are answering different questions ("this HTTP request was sent twice" versus "this *job* ran twice"), and the answer decides what the processor keys a retry on, so it must be argued in the proposal rather than settled implicitly while implementing. Step 26 deliberately left both handles open: the queue has no `defaultJobOptions` (attempts/backoff are part of the answer) and nothing enqueues a payment yet.

**Answered in the approved proposal (`docs/step-27-proposal.md`), before any code was written.** The pair is *not* reused as the worker mechanism: it is client-scoped, the worker's question is system-scoped, and Redis is the wrong side of the failure line for money when the authoritative state is already a row. The mechanism is `jobId = transaction.id` (a courtesy, because BullMQ forgets a job when its retention fires) plus a conditional `UPDATE` in Postgres as the arbiter, with the row deciding what each attempt does. Four decisions were put to review and approved as proposed — the rebuild fence (rebuild only when `now > submission_deadline` **and** a freshly loaded sequence equal to the recorded one, with a `tx_bad_seq`-on-rebuild restoring the previous record and stopping); four new `transactions` columns (`stellar_tx_hash` unique, `stellar_tx_sequence` as `varchar`, `submission_deadline`, `failure_reason`); the enqueue placed inside `PaymentsService.create`'s transaction before the commit; and the unique index over the hash. The review added one thing to that list, shipped in this step rather than deferred: a **three-second `commandTimeout` on the producer's Redis connection** (`PAYMENTS_QUEUE_COMMAND_TIMEOUT_MS`), because the enqueue runs inside the sender's row lock and an unbounded hang there is an availability cascade onto every payment from that sender. It is a *second* connection on purpose: ioredis arms `commandTimeout` for blocking commands too, and BullMQ's worker blocks for `drainDelay` (5s idle, up to 10s with a delayed job pending), so a few-second bound on the shared connection would turn every idle worker tick into an error plus a retry delay.

**Step 28 — Status polling job**
A separate repeatable BullMQ job (or a per-transaction delayed job scheduled right after submission) polls Horizon for confirmation using the stored `stellarTxHash`, updates status to `SUCCESSFUL` or `FAILED` with a `failureReason`, and triggers a notification.

**Answered in the approved proposal (`docs/step-28-29-proposal.md`) before the code was written.** The repeatable job won: a sweep whose work list is the `transactions` table (rather than one delayed job per payment, whose work list is Redis) is the only shape in which a flushed keyspace or a retention policy costs a *delay* rather than a payment that nothing will ever look at again. The schedule is a BullMQ job scheduler (`upsertJobScheduler`, id `confirmation-sweep`, one stable id per deployment so replicas do not multiply ticks) and it is **off by default** (`PAYMENTS_CONFIRMATION_INTERVAL_MS=0` registers nothing and says so at boot), because a process that starts writing payment verdicts on a timer has to be something a deployment opted into. A tick takes at most `CONFIRMATION_SWEEP_BATCH = 50` rows, oldest deadline first, and resolves them through `confirmation-triage.ts` — a pure function over what Horizon said, the row's recorded deadline and the clock: settled-and-successful → `SUCCESSFUL`; settled-and-not → `FAILED` with `landed-unsuccessful:<tx code>`; not found before the deadline plus `CONFIRMATION_GRACE_MS = 60_000` → wait; past it → `FAILED` with `not-found-after-deadline`; Horizon unavailable, or a hash with no deadline → `unresolved`, which writes nothing at all. The grace window is a reading of Horizon's ingest lag, not a product decision: erring towards waiting costs a minute, erring the other way claims a payment failed that then lands. The sender is told **after** the write, from the stored row, and a provider failure is logged and swallowed, which is what makes "one resolution, one SMS" a property of the compare-and-set rather than of a caller's timing. §5 of the proposal names exactly which of Step 27's `PROCESSING`-for-ever cases this closes (every row with a recorded hash) and which it deliberately does not (a claim that died before `recordEnvelope`, reported as `stuckWithoutHash` after five minutes and never written from the poller).

**Step 29 — Transaction status state machine**
Formalize the transitions (`PENDING → PROCESSING → SUCCESSFUL | FAILED`) as an explicit guard in the service layer — no direct status writes from anywhere else in the codebase, so the state machine can't be bypassed by a future shortcut.

**Answered in the same proposal.** `src/payments/services/transaction-status.ts` owns the table *and* every write of the column (`claimForSubmission`, `recordEnvelope`/`restoreEnvelope`, `markFailed`, `markSuccessful`), each a compare-and-set on the status it expects; the guards refuse an illegal move before the database is touched, and the `WHERE` clause is what actually decides a race. Creation is deliberately not a writer: a payment is created `PENDING` by the column's own `@default(PENDING)`, so the schema states what a payment starts as and the state machine states what it becomes — turning the rule on removed three restatements of the default (`PaymentsService.create` and two e2e fixtures) on the first run. The structural half is `npm run lint:status` (`src/payments/status-discipline.ts`, wired into `npm run lint` beside the money rule), which flags a `data: { status: ... }` on `transaction.create|createMany|update|updateMany|upsert` anywhere outside that file, a raw `SET status =`, and an exemption pointing at a file that has been moved, printing `file:line [rule] what to write instead`. It also prints what it *read* (`158 files scanned, 3 status writes in the sanctioned writer, 0 violations`) so a clean run cannot be confused with a scan that found nothing.


Done when: a payment submitted through the full flow (create → job picks it up → Stellar submission → polling confirms) lands as `SUCCESSFUL` with a real Testnet transaction hash you can look up on a Stellar Testnet explorer, and a deliberately-invalid payment (e.g. insufficient balance forced past the earlier check, or a bad destination) resolves to `FAILED` with a readable reason rather than hanging in `PROCESSING` forever.

**Step 30 — `GET /v1/payments/:id` and `GET /v1/payments`**

A list row carries six fields; `failureReason` and `stellarTxHash` are on the detail body only — a disclosure decision as much as a size one, since the reason is a raw machine code and the fewer rows carrying one, the fewer places it can be rendered as a sentence somebody wrote for a person.

## Day 6 — Credential hardening: transaction PIN, password, email, Google SSO (Steps 34a–34d)

**Where this fits.** Days 1–5 built the account, the wallet and the payment path; this day decides *who is allowed to move money* and *how they get back in*. It is scope added on top of the original Week 1 plan and kept deliberately separate from it: the four features sit after Step 34 and ahead of the buffer and the deployment steps (35–41), which keep their numbers, so every existing `Step N` reference in the source stays valid. The letter suffix is the same convention Step 7b used to slip in ahead of Step 8, and the four features are independent but ordered: each is finished (contract → data → service → audit → tests → done) before the next is started, and 34d comes last because it builds on the email identity 34c introduces.

**Groundwork built once, in 34a, then reused.**

- **One secret-hash utility.** `src/identity/otp/otp-crypto.ts` already owns CSPRNG generation and a self-describing scrypt hash (`scrypt$N$r$p$salt$hash`) with a constant-time comparison. Lift that hashing pair to `src/identity/credentials/secret-hash.ts` so OTP, PIN and password share one implementation and one format: OTP keeps today's parameters, the PIN reuses them, the password uses a stronger work factor. One format is one verifier, and no second implementation to keep in step.
- **A step-up guard.** `src/common/guards/` was reserved in Step 2 for exactly this. `StepUpAuthGuard` checks a short-lived, elevated claim that `TokenService` mints, so "prove the PIN again" is a second, narrow credential rather than a longer-lived session.
- **`denied`, with its first writer here.** `AUDIT_OUTCOMES` is `['ok', 'failed']` today and its spec says so in as many words - *"no `denied` until something denies"*. A step-up guard refusing a payment is that first refusal, so 34a adds `'denied'` rather than folding an authorization refusal into `failed`, which means "the operation did not happen". `src/audit/audit-events.spec.ts` pins both lists, so both change in the same commit.

**Step 34a — Transaction PIN: set at registration, proved before every payment**

**Contract.**
- `POST /v1/auth/register` gains a required `pin` beside `phoneNumber`; it is hashed and written with the row. The one credential every later payment depends on is collected once, up front. The `pin` must be **exactly four numeric digits** — `^\d{4}$`, no more, no fewer, digits only — and anything else is a 400 with a message that names the rule.
- `POST /v1/auth/pin/change` (JWT) — `{ pin }` sets the PIN when none exists; `{ currentPin, pin }` changes it. Both `pin` and `currentPin` must match `^\d{4}$`, so the 400 covers a PIN of the wrong shape as well as a malformed body; 409 when a change omits `currentPin` or it is wrong; 401 without a token.
- `POST /v1/auth/pin/verify` (JWT) `{ pin }` — the step-up call. 200 with a short-lived step-up token; 401 on a wrong PIN with the attempts left in the message; 429 once the PIN is locked. The PIN is never echoed back.
- `POST /v1/payments` now carries `StepUpAuthGuard`: with no fresh step-up token it is **403 `denied`**, not 401, because the caller is authenticated and has simply not presented the second factor.

**Data.** Add to `User`: `transactionPinHash String? @map("transaction_pin_hash")`, `transactionPinSetAt DateTime?`, `transactionPinAttempts Int @default(0)`, `transactionPinLockedUntil DateTime?`. Handwritten migration, then `prisma generate`. **No column records the PIN's length, and none should be added:** the column holds a scrypt hash (`scrypt$N$r$p$salt$hash`), whose length is a property of the *hash* and not of the PIN, and the four-digit rule is a validation rule, not a storage rule. A `pinLength` column, or a `char(4)` type on this one, would be a second and drifting statement of the same rule — the "fix" this constraint explicitly does not need — so the column stays a hash and nothing else. The policy — `PIN_LENGTH`, `PIN_MAX_ATTEMPTS`, `PIN_LOCKOUT_MINUTES`, `STEP_UP_TOKEN_TTL_MINUTES` — lives in `configuration.ts` beside the OTP constants, for the same reason those are there: the service and the message have to agree.

**Service.** `src/identity/pin/pin.service.ts` owns set/change/verify and the lockout arithmetic. The four-digit rule is enforced **before hashing, at the DTO/input-validation layer** — the same layer, and the same style, that already enforces the OTP code's shape: `verify-otp.dto.ts` declares a `CODE_PATTERN` built from `OTP_CODE_LENGTH` rather than written as a literal `\d{6}`, and applies it as `@Matches(CODE_PATTERN, { message: ... })`. The PIN copies that shape exactly: `PIN_LENGTH = 4` in `configuration.ts` beside `OTP_CODE_LENGTH`, and one `PIN_PATTERN` (`^\d{4}$`) declared in a single file — `src/identity/dto/pin-pattern.ts` — and imported by every DTO that takes a PIN (`RegisterDto`, the set-PIN and change-PIN DTOs). Never inlined per endpoint, so the rule has one place to change if a longer PIN is ever wanted, and the message moves with it rather than a stale `\d{4}` rejecting valid input. `PaymentsService` never learns what a PIN is: it is handed "this request carried a valid step-up claim", which is all `StepUpAuthGuard` establishes.

**Audit.** New literals with doc comments in `audit-events.ts` — `auth.pin.set` (ok), `auth.pin.changed` (ok), `auth.pin.verified` (ok), `auth.pin.failed` (failed) — written from the points named in each comment. No PIN, no hash and no phone number in `metadata`; identifiers and short codes only, per the `AuditLog` docstring. A **format** failure adds no fifth literal and no new outcome: a PIN that is not four digits is refused by the DTO with a 400 before any row is touched, so no audit-worthy action has happened — the same way a malformed OTP code is a 400 from `@Matches` today and never reaches the audit log. `auth.pin.failed` stays exactly what it is: a **correct-format** PIN that does not match the stored hash, which is a real attempt at the second factor and belongs in the log next to the lockout counter. Reusing `auth.pin.failed` for a malformed PIN would make "someone tried to guess the PIN" and "someone sent `12ab`" the same row, and a lockout report that cannot tell those apart is a report that lies.

**Tests.** Unit — `secret-hash.spec.ts` (round-trip, wrong secret, tampered format), `pin.service.spec.ts` (the hash never leaves the service, lockout after N, lockout expires, a change demands the current PIN), and a DTO spec that pins the shape rule itself: `1234` accepted, while `123` (three digits), `12345` (five), `12a4` and `abcd` (not digits-only), the empty string, and `1234 ` with a trailing space are each rejected. e2e — `test/pin.e2e-spec.ts`: register-with-PIN, set, change, change-without-current, verify, then wrong-then-locked, plus the four-digit rule at **both** write paths — registration rejects a three-digit, a five-digit and an alphanumeric PIN with a 400 while a valid four-digit one is accepted and usable, and the same three are rejected at PIN-change with the valid one accepted. `test/payments.e2e-spec.ts` gains the two guard cases: no step-up is 403, a fresh step-up is 202. Two files hold the parts that are about the *contract* rather than the flow: `test/api-docs.e2e-spec.ts` asserts that the header `POST /v1/payments` demands is documented as **required** in `GET /api/docs` (a header the route requires and the document omits is half a contract, and the missing half is the one that answers 403), and `test/audit.e2e-spec.ts` triggers both PIN rows through the API — a wrong guess and a real change — so `auth.pin.changed` and `auth.pin.failed` are written by the application rather than assumed, and asserts that neither row carries a PIN.

**Done when:** the PIN is written at registration; registration and PIN-change both reject any PIN that is not **exactly four numeric digits**, with a 400, while a valid four-digit PIN hashes and verifies exactly as it did before; every `POST /v1/payments` without a fresh step-up is refused and audited; a wrong-PIN burst locks and is audited rather than merely answered with an error.

**Step 34b — Password: a second way in, changeable and recoverable**

**Contract.**
- `POST /v1/auth/password/change` (JWT) — `{ password }` sets one when none exists; `{ currentPassword, password }` changes it. 200/400/409/401.
- `POST /v1/auth/login/password` `{ phoneNumber, password }` — the password sign-in, answering the same token pair the OTP login answers. 200; 401 for a wrong password, with one message for "no such user" and "wrong password" for the reason refresh failures share one; 429 when the number is over its attempt allowance; 403 when the account is suspended.
- `POST /v1/auth/password/reset` `{ phoneNumber }` — begins a forgot-password reset by texting a code. Answers 202 whether or not the number exists, so it is not an existence oracle.
- `POST /v1/auth/password/reset/confirm` `{ phoneNumber, code, newPassword }` — 200 on success; 400/429 mirror the OTP verify paths.

**Data.** No migration: `User.passwordHash` already exists and is documented as nullable *"until (and unless) password login is added"* — this is that step, so the column simply stops being null for accounts that set one.

**Service.** `src/identity/password/password.service.ts` hashes through `secret-hash` (stronger parameters than the PIN) and enforces `PASSWORD_MIN_LENGTH` from `configuration.ts`. The reset reuses `OtpService` to issue and check the code and `NotificationsService` to deliver it — a reset code is an OTP with a different purpose, not a second OTP system. The login draws on the OTP rate limiter's Redis counter, so a password guess is priced like a code guess.

**Audit.** `auth.password.set` (ok), `auth.password.changed` (ok), `auth.password.login` (ok), `auth.password.reset.requested` (ok), `auth.password.reset.completed` (ok). A refused password login is `auth.password.login` with outcome `denied` — the outcome 34a introduced — which keeps the one `auth.login` entry meaning "a sign-in succeeded".

**Tests.** Unit — `password.service.spec.ts` and a policy/DTO-validation spec. e2e — `test/password.e2e-spec.ts`: set, change, change-without-current, login success, login wrong, login over the allowance, a reset request for a known and an unknown number (both 202), reset confirm, and reset with a bad code. Reset rows land on `auth.password.*` and carry neither the password nor the code.

**Done when:** an account can sign in with a password as well as a code, change it by proving the current one, and recover it by SMS — each path audited.

**Step 34c — Email: a verified address and a second delivery channel**

**Contract.**
- `POST /v1/auth/email` (JWT) `{ email }` — attaches or replaces the account email and sends a verification code to it. 200; 400 for a malformed address; 409 when another account has already verified it; 429 once the address's send allowance is spent (3 per 15 minutes, the OTP limiter's counter, keyed on the address); 503 when the email was not sent.
- `POST /v1/auth/email/verify` (JWT) `{ code }` — confirms the address. 200; 400 for a wrong or expired code; 429 when the attempts are spent.
- Payment receipts — the settlement path that already texts the sender (`NotificationsService.sendPaymentResult`) now also sends to a verified email when one exists.

**Data.** Add to `User`: `email String? @unique @map("email")`, `emailVerifiedAt DateTime? @map("email_verified_at")`. Handwritten migration. Uniqueness is on the stored, lower-cased address, following the one-spelling-per-identity rule `phoneNumber` already follows.

**Service.** `src/identity/email/email.service.ts` issues and checks the verification code. A new `EMAIL_SENDER` token, mirroring `SMS_SENDER`, is bound in `NotificationsModule`, so the provider — SMTP today, a transactional API tomorrow — is one line and the e2e tests replace the binding rather than the network. `NotificationsService` gains `sendEmailVerification(to, code)` and an email arm of `sendPaymentResult`, with the wording living beside the sender as the SMS wording does.

**Audit.** `auth.email.set` (ok) and `auth.email.verified` (ok). The address is a personal identifier: `metadata` carries the `userId`, not the address, matching the rule that no phone number appears in the clear either.

**Tests.** Unit — `auth.service.spec.ts` for the send allowance and its refusals, `email.service.spec.ts`, an address normalisation/validation spec, and `notifications.service.spec.ts` for the email text and the from/to. e2e — `test/email.e2e-spec.ts`: set, verify, a wrong code, expiry, a duplicate address, the send allowance running out, and a payment whose settlement produces both an SMS and an email through the substituted sender. `test/audit.e2e-spec.ts` gains the `auth.email.*` rows.

**Done when:** a user can attach and verify an email, and a settled payment reaches it, with both events in the audit log.

**Step 34d — Google SSO: sign up and sign in with a verified Google email**

**Where this fits.** This is the last piece, and it depends on 34c: a Google-authenticated email *is* a verified email, so an account created this way lands in exactly the state 34c already defines — `emailVerifiedAt` set, no emailed code to spend, no second verification screen — and nothing new has to be invented for "is this address real". It is a second way in, in the same spirit as the password path in 34b, with one difference: the proof that the person owns the address comes from Google, not from their memory of a secret.

**Contract.**
- `POST /v1/auth/google` `{ idToken }` — the ID token from the client's Google Sign-In flow. The server verifies it against Google's public keys and the expected audience (the client ID) and reads the `email` and `email_verified` claims; a client-asserted email is never trusted, only a claim inside a token this API verified itself. 200 with the token pair `POST /v1/auth/login` already answers, plus one added field (below); 400 when the token is missing, malformed, expired, or for the wrong audience; 403 when `email_verified` is not `true` — an unverified Google address is evidence of nothing, so it is refused rather than treated as a verified account email.
- Account exists for that verified email → **sign in**. Same treatment as 34b's password login: a second route to a session, not a second account. If the row exists but its address was never verified, Google's proof is at least as good as the code 34c would have mailed, so the login stamps `emailVerifiedAt` rather than dead-ending the user.
- No account → **create one**, with the Google address as the verified email and no password (there is no password, and inventing one would be a credential the user cannot use). The account still needs a PIN to transact, per 34a's "PIN mandatory at registration" default, so the response signals the client to route into PIN setup rather than skipping it: `nextStep: 'SET_PIN'`, absent when an existing PIN-holding account signs in. A client that ignores the signal is not left insecure — 34a's `StepUpAuthGuard` already refuses a payment with no PIN — it just gets the 403 at payment time instead of the screen at sign-in time.

**Data.**
- `oauthProvider String? @map("oauth_provider")` and `oauthSubject String? @map("oauth_subject")` on `User`, with `@@unique([oauthProvider, oauthSubject])`. `oauth_subject` is Google's stable `sub`, not the email: an address can change on Google's side (a name change, a school address that expires) while `sub` does not, so a repeat login looks the account up by the pair and never by the address. The `email` column stays exactly what 34c made it — the source of truth for every email behaviour — and `oauth_subject` is *only* the lookup key for a returning Google user. Postgres allows many NULLs in a unique index, so the existing phone-first rows (both columns NULL) collide with nothing.
- `phoneNumber` becomes nullable (`String? @unique @map("phone_number")`). This is forced by the requirement, and it is the largest single ripple in the step: "sign up with nothing but a Google account" means an account with no phone number, and the column is `NOT NULL` today (`prisma/migrations/20260926073441_init` writes `"phone_number" TEXT NOT NULL`). It is one `ALTER COLUMN … DROP NOT NULL`, and the unique index is unaffected — which is the intended behaviour, stated here so it is not later mistaken for an oversight: `NULL`s are distinct in a Postgres unique index, so `String? @unique` permits any number of phone-less accounts to coexist, while the guarantee that matters is untouched — uniqueness still applies to every non-null value, so two spellings of one number still collide as they do today. Three ripples, each fixed by name rather than discovered later:

- **`SessionResponseDto.phoneNumber` becomes optional.** `src/identity/dto/session-response.dto.ts:29` is `phoneNumber!: string` today; it becomes `phoneNumber?: string` with `nullable: true` on its `@ApiProperty`, so the published OpenAPI document stops promising a value the row is not guaranteed to have, and `LoginResponseDto.phoneNumber` (`src/identity/dto/login.dto.ts:46` — the same four fields, and the shape 34d's Google response reuses) changes in the same commit. `AuthService.session` (`src/identity/auth.service.ts:622-628`) passes `user.phoneNumber` straight through, so once the type is optional the `null` is a legal value rather than a lie, and the assumption being corrected is recorded at the field itself: the only 200 bodies that legitimately carry `phoneNumber: null` are the ones for a Google-created account, and nothing server-side formats the value before it is serialized, so no extra mapper branch is needed beyond the DTO type and its doc note.
- **Every E.164 read of a *stored* number, listed.** (1) `src/identity/auth.service.ts:625` in `session()` — passes the value to the now-optional field above. (2) `src/payments/services/payments-confirmation.service.ts:163`, which selects `sender: { select: { phoneNumber: true } }` for the settlement sweep and feeds it to `NotificationsService.sendPaymentResult` at `:345`; that method's signature is `(phoneNumber: string, …)` (`src/notifications/notifications.service.ts:72`) and its SMS arm masks the value through `maskPhoneNumber` (`src/common/phone/phone-number.ts:103`, which calls `.length` and so throws on `null`), so the guard belongs at that call site — a phone-less sender's result is skipped on the SMS arm, where 34c's verified-email arm is what still reaches them — rather than `maskPhoneNumber` being taught to accept `null`. (3) `src/payments/services/recipients.service.ts:160`, where a *searched* E.164 is matched against the column: a `NULL` column simply never matches, which is the answer we want, because a phone-less account must not be discoverable by typing a number. Nothing else reads a stored number: everywhere else the normalizer only ever sees submitted input, which is never absent — `src/identity/auth.service.ts:144/364/481/528` and `src/payments/recipients/recipient-query.ts:120`, all of them through `AuthService.normalize` (`src/identity/auth.service.ts:645`), which stays a `string`-in function.
- **Payability keeps one definition, and it is not loosened here.** `recipients.service.ts` stays the single source of truth: `PAYABLE_RECIPIENT_FILTER` (`src/payments/services/recipients.service.ts:67-70` — `status: ACTIVE` **and** `phoneVerifiedAt: { not: null }`) is what `assertPayableRecipient` (`src/payments/services/recipients.service.ts:241`) queries, and both readers go through it — `GET /v1/recipients/:id` (`src/payments/services/recipients.service.ts:211`) and `POST /v1/payments` (`src/payments/services/payments.service.ts:231`). No other path may independently re-check `phoneNumber` presence as a proxy for payability: that would be a second, drifting rule, and it would also misjudge an account whose number is real but unverified. A Google-only account is a real account with `phoneNumber: null`, not an error state — it is simply not yet payable.
- Provisioning, and the function the Google path calls. `AccountProvisioningService.provisionFor`'s call site on the **phone** path is unchanged by this step: `AuthService.verifyOtp` still calls it from the same place (`src/identity/auth.service.ts:446`), after the write that sets `phoneVerifiedAt` and flips `status` to `ACTIVE` in one go (`src/identity/auth.service.ts:398`) — the write `src/identity/identity.module.ts` explains `WalletModule` is imported for. Google sign-up does **not** call `provisionFor` at all: there is no OTP to verify, so the precondition `provisionFor` documents — a caller that has already committed "this account is verified" — has nothing to check, and a route calling it would be asserting a fact it never proved. The Google route calls the shared account-creation helper instead: **`AccountsService.createVerifiedAccount(input)`**, a new `src/identity/accounts/accounts.service.ts` holding the "new account" logic 34a, 34c and 34d all reach for rather than a second creation path beside `register`. That helper writes the row already `ACTIVE` — `emailVerifiedAt` set, `passwordHash` null, `phoneNumber` null, the `oauthProvider`/`oauthSubject` pair written — and then makes the same provisioning hand-off `verifyOtp` makes, which is where the wallet comes from. The trigger therefore stays exactly what this step already names — **the write that flips `status` to `ACTIVE`**, not the `phoneVerifiedAt` column — so the OTP path (which sets both in a single write) is unaffected, and a Google account provisions on its own verification.
- `handle` is untouched and stays nullable: a Google account arrives with none, and `handle` is still the payment recipient identifier, so claiming one remains part of onboarding before money can be received.

**Service.** `src/identity/google/google-auth.service.ts`, split the way the repo already splits auth — the route is one delegation from `AuthController` to a service that owns the logic and the status codes. Verification is a **seam, not a call**: a `GOOGLE_TOKEN_VERIFIER` token mirroring `SMS_SENDER` (the README's "the one line to change to swap the provider"), bound in the identity module and replaced in e2e so a test never reaches Google and never needs a live token. The real binding verifies the signature against Google's JWKS and checks the audience against `GOOGLE_CLIENT_ID`, read through `configuration.ts` and required by `validation.schema.ts` so a missing client ID fails at boot rather than at the first sign-in. The service then hands off to the **existing** account-creation path — the same "new account" logic 34a and 34c use — skipping only the password and phone-verification steps and never the PIN requirement, rather than growing a second creation path beside it. A Google address that has changed does not rewrite the stored email: the account's address is 34c's to change, through 34c's verified flow, so a login after a Google-side change finds the row by `oauth_subject` and leaves the address alone.

**Audit.** Two new literals with doc comments in `audit-events.ts`, in the same `auth.*` vocabulary and comment style as 34a–34c: `auth.google.signup` (ok) — a new account created via Google SSO — and `auth.google.login` (ok) — an existing account signed in via Google SSO, the row `auth.password.login` has as its counterpart. Both go into `AUDIT_ACTIONS`, into `audit-events.spec.ts`'s pinned vocabulary and into `test/audit.e2e-spec.ts`, in the same commit, exactly as 34a–34c's events do. `metadata` carries the internal `userId` and nothing else — **no ID token, no email and no Google `sub`**: the token is a live credential, the address is a personal identifier (the rule 34c applies to email and the schema applies to phone), and the subject ID would be a third identifier for the same person that the account's own id already stands in for. A refused token writes no row at all — a 400/403 is answered before anything happens at the account level, the same shape as 34a's malformed PIN.

**Tests.** Unit — `google-auth.service.spec.ts` against a substituted `GOOGLE_TOKEN_VERIFIER`: a verified claim creates, a known `oauth_subject` signs in, `email_verified: false` is refused, and an expired or wrong-audience token is refused. e2e — `test/google.e2e-spec.ts`, with the verifier replaced so all four cases are deterministic: (a) a first-time Google sign-up creates an account with `emailVerifiedAt` set, `passwordHash` null and `nextStep: 'SET_PIN'` in the response; (b) a repeat Google login finds the row by `oauth_subject` — proven by signing in after the Google address *changes*, which matching on email would fail; (c) `email_verified: false` is a 403 and creates nothing; (d) an invalid, expired or wrong-audience token is a 400. The file then does the two steps together: a payment by the new account before a PIN is set is refused with a `denied` row, and the same payment succeeds once 34a's PIN is set — so "PIN still required" is a fact about the system rather than a claim about the spec. `test/audit.e2e-spec.ts` gains the `auth.google.*` rows, asserted to carry no token, no address and no subject.

**Done when:** a new user can sign up with nothing but a Google account, lands with a verified email and no password, and cannot pay until a four-digit PIN is set; a returning Google user is signed in matched by `oauth_subject`, without re-entering any credential. A Google-only account has `phoneNumber: null`, is not payable until it adds and verifies a phone, and nothing crashes or silently misbehaves on the null in between.

Delivery is proven on the message itself — *attaches the address lower-cased and unverified, and emails the code to it* submits `  ADDRESS@EXAMPLE.COM  ` the way a keyboard does it and asserts that the response and the row both hold the normalized spelling, that `email_verified_at` is still `null` (the two columns are two facts, not one), and that exactly **one** message went to that address: from the configured `email.from`, subject matching `/verification code/i`, body containing the six digits — and the code **absent from the response body**, because an echoed code is a code anyone who can read one log line has. Confirming is a second write and a second row: *confirms the attached address with the code the email carried* fills the column with "now" (the answer and the row are the same instant to within a second) and writes `auth.email.verified` beside the attach's own `auth.email.set`, with the address provably nowhere in either row. The refusals are each provoked rather than asserted about, and each is one a client can act on: a wrong code is a **400** counting down "4 attempts remaining" that costs an attempt and not the address; an expired code is a **400** matching `/expired/i` whose row is then **consumed**, so a dead code cannot be presented twice or become the row a later allowance is counted against; the fifth wrong guess is a **429**, and the *correct* code is refused afterwards with "No verification code is outstanding" — the limit is five wrong guesses, not five and then the right one; a second confirmation of an already-verified address is a **409** "already verified", answered before the code is even looked at, because "this is already done" is the useful thing to say; confirming with nothing attached is a **409** "No email address is attached"; an address another account already holds is a **409** "already in use" that leaves the second account's `email` `null` and the address's message count at **1**, so a refused attach mails nobody; and `not-an-address` is a **400** whose message echoes what was sent (`"not-an-address" is not a valid email address.`) with no code generated at all, because the shape rule runs before any write. The second delivery channel — the half that makes a verified address worth holding — is shown over the **real sweep**, not by reading `notify`: with a verified address attached, `PaymentsConfirmationService.sweep()` on a settled payment sends a receipt to the address as well as the text to the number, and `receipts[0].body` is asserted **equal to** the texted body — one template, two transports — with both filters keyed on subject `/went through/` so that "a receipt reached this mailbox" stays a different claim from "a verification code did". The negative half is the rule the two columns exist for: replacing the address writes the new one **unverified**, so the next settlement texts the number and emails **nobody**, and the account's two attaches are still two rows that hold neither address in the clear.
