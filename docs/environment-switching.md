# Switching environments: staging → production

**Who this is for:** whoever has to take Cashping from the staging deployment described by
`render.yaml` to a real, mainnet deployment. It answers three questions in one place — what differs
between the two environments, what has to change and in what order, and what must *never* be reused
as-is.

It is a companion to, not a replacement for:

- `docs/pre-production-hardening.md` §3 — the staging smoke test. Its prerequisite table (the nine
  `sync: false` values) is the setup half of this document; this one is the teardown half.
- `docs/kms-credentials-explained.md` — what a custody credential is, why it is sealed, and why the
  key can never be rotated by this application.

**There is no production deployment in this repository, and this document does not create one.** The
`render.yaml` here describes *staging*. Everything below is either a non-secret literal in that file
or a `sync: false` value answered in the Render dashboard. Where a production value is a fact nobody
has yet — Circle's mainnet issuer above all — this document says so rather than guessing, because a
guessed value in this file is worse than an empty one.

## 1. This environment is staging. Here is how to tell.

| Signal | Staging (this repo) | A production deployment |
| --- | --- | --- |
| Host | `cashping-staging-udht.onrender.com`, not linked from anywhere | a real, public hostname |
| Network | `STELLAR_NETWORK=TESTNET` — no real money can move | `STELLAR_NETWORK=PUBLIC` |
| Plan | all three resources `plan: free`; the database expires 30 days after creation | paid, backed-up, persistent |
| Data | disposable — losing it costs nothing | the opposite |
| Docs | `ENABLE_SWAGGER=true`; `/api/docs` is open | `false` |

If any row reads "production" but the service is the staging service, stop: that is the confusion this
document exists to prevent.

## 3. Why staging runs `NODE_ENV=production` — and why it is still staging

This is the single most misread value in the file, so it gets its own section.

`render.yaml` sets `NODE_ENV=production` on the staging service **on purpose**. The boot-time custody
guards from Step 18 fire *only* under `production`, and `AWS_ENDPOINT_URL` is refused at boot when
`NODE_ENV=production` and a KMS key id are both set. An environment that never exercised those guards
would be the first place they ever fired — a real deployment. Staging sets `NODE_ENV=production` so
the guards are rehearsed continuously, so a misconfiguration is caught in staging and not in the one
environment that matters.

What that does **not** do is make staging production. `NODE_ENV` controls *which code paths and guards
run*; it does not by itself point the app at real money. That is a different set of values, and all of
them still say "test":

- `STELLAR_NETWORK=TESTNET` — nothing signed here can move a real cent.
- `STELLAR_USDC_ISSUER` is a Testnet issuer — the throwaway staging keypair in §6b.
- The datastores are Render free-tier and expiring.
- Swagger is open.

So `NODE_ENV=production` on staging means "run as carefully as production", never "this is
production". A real deployment keeps `NODE_ENV=production` **and** changes every one of those four
bullets.

## 4. Production must use a **separate** KMS key — and its own IAM principal

Every account's Stellar seed is sealed under `AWS_KMS_KEY_ID`. That key is the root of custody: hold
it and you can unwrap every wallet in the environment it belongs to. Two consequences follow, and
both are about *blast radius* rather than best practice:

- **A separate key per environment.** If staging and production shared one KMS key, then anything that
  can reach the staging *service* — staging credentials, a staging misconfiguration, a person with
  staging dashboard access — could in principle unwrap a **production** user's seed. The staging key
  is the one most likely to leak (it is what people test with), so it must never be able to open a
  production account. Separate keys make a staging compromise a staging problem, which is the entire
  point of having a staging environment.
- **A separate IAM principal, scoped to that key.** The staging access key pair holds exactly
  `kms:GenerateDataKey`, `kms:Decrypt` and `kms:DescribeKey` on the staging key ARN and nothing else
  (`README.md` → *What the KMS credentials are allowed to do*). The production principal is a
  **different** access key with the same three actions on the **production** key ARN. Never grant one
  principal both keys.

And the constraint that outlives both: **the master key cannot be rotated by this application.**
Nothing re-wraps an existing row, so disabling or rotating the old key strands every account sealed
under it. Rotate the *access key* if credentials leak; treat the KMS key as fixed for the life of the
data it protects — which is why the production key deserves its own deliberate creation step rather
than a copy of the staging one.

## 5. The email provider — staging runs Brevo SMTP, not SendGrid

Worth stating plainly because it is easy to misremember: **as configured today, staging sends through
Brevo's SMTP relay** (`EMAIL_SENDER=smtp`, `SMTP_HOST=smtp-relay.brevo.com`, `SMTP_PORT=2525`). The
`RESEND_API_KEY` is present in `render.yaml` but is *not read* while `EMAIL_SENDER=smtp`.

The code carries four senders — `resend`, `sendgrid`, `smtp`, `mailtrap` — selected by `EMAIL_SENDER`.
The history, for the record:

- **Resend** was the original production plan (commit `c089ee4`, and the `render.yaml` comment). It
  needs a *domain* verified in Resend's dashboard (SPF/DKIM) before it will deliver to arbitrary
  inboxes; until `cashping.app` is verified it can only mail Resend's own account address.
- **SendGrid** was added as an alternative sender (a key alone configures it, given a Single Sender
  Verification). It is **not** what staging currently runs.
- **SMTP → Brevo** is what staging runs now (commit `adbad82`): a single-sender-verified address, no
  sending domain required — which is why it was chosen for an environment that has to mail arbitrary
  test inboxes.

**For production**, pick one and make it domain-verified: set `EMAIL_SENDER` to that provider, set
`EMAIL_FROM` to the address verified on the production domain, and supply that provider's credential.
Do not carry `EMAIL_SENDER=smtp` into production on the strength of the Brevo relay — it is a
test-environment arrangement.

## 6. The USDC issuer, in detail

This deserves more than a table row because there are **three** issuers in play and only one is
correct for a given environment. An issuer public key is not a code: `USDC:<A>` and `USDC:<B>` are
two different assets that happen to share the name `USDC` — which is why the code matches a balance on
code *and* issuer (`usdc-trustline.ts`), and why the wrong value fails quietly as a zero balance
rather than loudly.

### 6a. Circle's Testnet issuer — what this app was built against

```
GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5
```

The genuine USDC asset Circle issues on Stellar **Testnet**, and the value `.env.example` ships
(and which `render.yaml` carried until staging moved to §6b). It is real within its network and worth
nothing outside it. Its one practical limitation: there is **no automatable public faucet** for it — Circle's faucet is a browser +
reCAPTCHA flow with per-address limits, so an account can only be funded by a human in a browser
(`docs/pre-production-hardening.md` §3.0(c)), not by a script or an operator on demand.

### 6b. The staging test-only issuer — NOT Circle's asset

```
GD7LC7NGLRLX23Z6PWGVSYD6WYLHH27AMLEKQUMELCZG3I2KIIQVYKHL
```

Created for staging so the environment can **mint test USDC on demand** — the running application can
never mint (there is no issuer secret anywhere in the backend; the only funder is friendbot, which
pays XLM). This keypair is a throwaway that happens to issue a token with the code `USDC`; it is
**not real USDC**, exists only on Testnet, and custodies nothing. Its secret is held outside the repo
(a developer's local `.env`, used by the offline helper under `.temp/`).

Its *public* key is a `sync: false` value entered in the Render dashboard, not committed to
`render.yaml` — so no Testnet issuer can be carried into a production file by accident.

Two things about using it on staging:

- **It makes staging differ from production on purpose.** That is the intended trade — free test
  funds, at the cost of no longer proving that Circle's *real* asset is what lands.
- **The issuer must be set before any account is registered.** A trustline is on-chain and permanent;
  the app creates exactly one, at activation, against whatever issuer was configured *then*. A wallet
  provisioned against the old issuer has a line the new configuration will never match, so it reads
  as a zero balance forever. Order: change the issuer → register fresh accounts → mint.

### 6c. Circle's mainnet issuer — the value we do **not** have

**This value is not yet known and must not be guessed.** At the moment of the real production launch,
read it from Circle's current official source — starting at
<https://www.circle.com/en/usdc/developers> — and set `STELLAR_USDC_ISSUER` to exactly that.

Three ways this goes wrong, all avoidable:

- **Never** carry a Testnet value (6a or 6b) into production. A mainnet deployment pointed at a
  Testnet issuer will fail to find any such asset — or, if anything by that key exists, settle the
  wrong one.
- **Never** take the value from a blog post, a screenshot or a memory. Only from Circle's own
  documentation, checked on the day.
- **Never** assume the Testnet and mainnet issuers are related. They are different keypairs.

Staging's value lives in the dashboard, not in a file (§6b), so a Testnet issuer cannot be carried
into production by accident. Set the production value the same way: one explicit, reviewable
dashboard value, never left implicit.

## 7. The funder — a production gap to know about before you plan the launch

Every new account gets its first XLM from an `AccountFunder` (`src/wallet/provisioning/account-funder.ts`).
That port exists precisely because the funder is the part that changes between networks: Testnet has
friendbot, an operator's local node has either, and **production funds new accounts from a treasury
account the operator keeps topped up**.

**Today only `friendbot` is implemented** (`WalletModule` binds it). The port, the error types
(`AccountFundingUnavailableError` vs `AccountFundingMisconfiguredError`) and the docs all anticipate a
`treasury` binding, and the design comment names "Testnet friendbot and a real treasury account" as the
first two bindings — but the treasury funder is *not written*. So this is not a value to change; it is
**code to build** before a mainnet deployment can provision anyone:

- On `STELLAR_NETWORK=PUBLIC` there is no friendbot, and `STELLAR_FRIENDBOT_URL` pointing anywhere is
  wrong. The current code's tested behaviour for "a public-network deployment with no treasury
  configured" is `AccountFundingMisconfiguredError` — provisioning refuses, by name, rather than
  timing out against an endpoint that does not exist. Correct, and a hard stop.
- The treasury account must be funded with real XLM, funded *by an operator*, and its secret sealed
  like any other custody secret. That is a deliberate operational process nobody can script away.

Treat this as the top line of the go-live checklist, not an afterthought: an environment that cannot
fund a new account cannot onboard anyone.

## 8. Going live, in order

Order matters in three places — the KMS key, the USDC issuer, and registration-before-funding — for
the reasons in §4 and §6. The rest is bookkeeping.

1. **Decide and create the production custody key.** A **new** KMS key (§4), in the production region,
   plus a **new** IAM principal holding only the three custody actions on that key. Never the staging
   key, never the staging principal.
2. **Build the treasury funder** (§7) and bind it for `STELLAR_NETWORK=PUBLIC`. Do this before touching
   a mainnet account, because there is nothing else that can create one.
3. **Look up Circle's mainnet USDC issuer** from Circle's official source (§6c) — on the day. Do not
   proceed with a placeholder.
4. **Provision infrastructure:** paid Postgres with backups (no 30-day clock), persistent Redis, a
   real hostname, `NODE_ENV=production`.
5. **Set every non-secret literal** for the production deployment — the `render.yaml`-equivalent file
   or the dashboard — from the right-hand column of the matrix in §2. `ENABLE_SWAGGER=false`.
   `STELLAR_NETWORK=PUBLIC`. `STELLAR_HORIZON_URL=https://horizon.stellar.org`. The mainnet issuer from
   step 3.
6. **Set every secret fresh.** Generate a new `JWT_SECRET`; new `AWS_ACCESS_KEY_ID` /
   `AWS_SECRET_ACCESS_KEY` (step 1); live `AFRICASTALKING_API_KEY` + live `AFRICASTALKING_USERNAME`;
   a `CORS_ALLOWED_ORIGINS` listing only the real production frontend; the chosen email provider's
   credential and a domain-verified `EMAIL_FROM`; a production `SENTRY_DSN` and
   `SENTRY_ENVIRONMENT=production`.
7. **Boot and read the `[boot]` markers** the way `docs/pre-production-hardening.md` §3.1 describes —
   the KMS probe above all. A fresh key that the principal cannot reach answers exactly like a deleted
   one.
8. **Register nothing until steps 1–6 are done.** The issuer and the funder both have to be right
   *before* the first account, because both are baked into that account's on-chain state and cannot be
   changed afterwards without a fresh account.

## 9. What must NEVER be reused as-is

The shortest useful version of this document:

- **No secret.** Not `JWT_SECRET`, not `AWS_SECRET_ACCESS_KEY`, not any SMTP/Resend/SendGrid/
  Africa's Talking key, not the staging `STELLAR_TEST_ISSUER_SECRET`. Every one is per-environment and
  must be newly created for production.
- **No key.** `AWS_KMS_KEY_ID` must be a **separate** key from staging's (§4). The whole point of
  staging is that it can be compromised without touching production custody.
- **No issuer.** `STELLAR_USDC_ISSUER` must be Circle's **mainnet** issuer, looked up fresh (§6c) —
  never `GBBD47…`, never `GD7LC7…`, never a guess.
- **No funder.** Never point a production deployment at a faucet; build the treasury funder (§7).
- **No swagger, no free tier, no testnet.** `ENABLE_SWAGGER=false`, paid and backed-up datastores, and
  `STELLAR_NETWORK=PUBLIC`.

### In plain words

This environment is **staging**. It runs `NODE_ENV=production` only so the custody guards are
rehearsed — that single value is not a sign of a real deployment and must not be read as one. To go
live: create a *new* KMS key and a *new* custody principal; **build** the treasury funder, because
production has no faucet; look up Circle's *mainnet* USDC issuer on the day from Circle's own docs and
write it in explicitly; stand up paid, backed-up datastores behind a real hostname; and set every
secret fresh, in this order — key and principal, then funder, then issuer, then infrastructure, then
registration. What must never be carried over: any secret, the KMS key, the USDC issuer, or a faucet.
A staging value copied into production is not a shortcut; for the KMS key and the issuer it is a
different, wrong system that happens to boot.
